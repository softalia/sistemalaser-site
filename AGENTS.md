# Sistema Laser Site - Agent Guidelines

## Purpose

This repository contains the static public website for Sistema Laser. Keep the
site simple, SEO-focused, and compatible with GitHub Pages.

## Source And Build Model

- The repository root is the editable source for the static pages.
- `dist/` is the generated public artifact and must not be edited by hand.
- `make build` recreates `dist/` from source files.
- `make validate` runs the build and validates generated pages, structured data
  and internal links.
- `CNAME` must stay versioned at the repository root. The build copies it to
  `dist/CNAME`, which GitHub Pages uses for the custom domain.
- Do not version generated files in `dist/`.

## Canonical Commands

- List available commands: `make help`
- Build the public site: `make build`
- Validate the generated site: `make validate`
- Serve the generated site locally: `make serve`
- Remove generated output: `make clean`
- Convert new assets to WebP: `make convert-assets-new-to-webp`

Use `make serve` for browser testing. Do not open HTML files directly with
`file://`, because `blog.html` fetches `blog/posts.json` and needs HTTP.

## Blog

- `blog/posts.json` is the canonical editorial source for posts.
- Do not create or edit `blog/*.html` in source. Blog post HTML pages are
  generated into `dist/blog/`.
- Each post entry should keep:
  - `slug`
  - `title`
  - `description`
  - `seoTitle`
  - `seoDescription`
  - `date`
  - `modified`
  - `author`
  - `category`
  - `tags`
  - `heroCopy`
  - `readingTime`
  - `image`
  - `url`
  - `contentHtml`
- Keep internal links in `contentHtml` relative to the generated post location,
  such as `../agenda-locacoes.html`.
- After changing `blog/posts.json`, run `make validate`.

## FAQ

- `faq/faq.json` is the canonical editorial source for frequently asked questions.
- Each section identifies the related public pages and owns the question IDs, questions and answers for that context.
- `scripts/build-faq.mjs` generates `dist/faq.html`, copies the public JSON to `dist/faq/faq.json`, and replaces the legacy FAQ blocks and FAQPage schemas in generated pages with the matching section from the JSON source.
- Do not edit FAQ text directly in rendered page markup. Update `faq/faq.json` and run `make validate`.
- Whenever a page gains, removes or materially changes a feature, plan, workflow, audience or commercial claim, review its related FAQ section in `faq/faq.json` in the same change. Add, revise or remove questions so the FAQ remains accurate and discoverable.

## Shared Layout

- The shared top navigation lives in `assets/js/header-2026.js`.
- The shared footer lives in `assets/js/footer-2026.js`.
- Prefer improving these shared scripts over duplicating header or footer markup
  in individual pages.
- These scripts must work from both root pages and generated `/blog/` pages.

## SEO Requirements

- Preserve canonical URLs using `https://www.sistemalaser.com.br`.
- Keep Open Graph and Twitter metadata aligned with each page's purpose.
- Blog posts generated by `scripts/build-blog.mjs` must include Schema.org
  `BlogPosting` and `BreadcrumbList`.
- Core pages may include broader Schema.org entities such as `Organization`,
  `SoftwareApplication`, `Product`, `FAQPage`, `Review` and `BreadcrumbList`.
- Update source data or build scripts rather than manually patching generated SEO
  in `dist/`.
- Keep `robots.txt`, `llms.txt`, sitemap generation and blog feed generation
  consistent with public URLs.
- Keep `faq.html` and `faq/faq.json` represented in the sitemap, `llms.txt` and validation when changing the FAQ build.

## Assets

- Place newly received source images under `assets/new/`.
- Run `make convert-assets-new-to-webp` to convert supported images to WebP.
- The conversion script removes each original file after a valid WebP is written.
- Keep final public assets under `assets/`, using descriptive lowercase filenames
  where practical.
- Avoid committing `.DS_Store` or other local system files.

## GitHub Pages

- GitHub Pages should be configured with `Source: GitHub Actions`.
- The publishing workflow is `.github/workflows/build-site.yml`.
- The workflow builds and validates `dist/`, uploads it with
  `actions/upload-pages-artifact`, and deploys it with `actions/deploy-pages`.
- Do not replace this with branch-root publication unless the build model is
  intentionally changed.

## Editing Guidance

- Preserve the existing visual language in `assets/css/site-2026.css`.
- Keep page changes scoped and avoid unrelated rewrites of minified legacy files.
- Prefer structured JSON and generator changes over ad hoc string edits for blog
  output.
- Treat a dirty worktree as user work unless you know the changes are yours.
- Before finishing, run `make validate` when changes affect pages, blog content,
  assets used by pages, build scripts, SEO metadata, links or shared layout.
- Use this meta property for Open Graph images in new pages and blog posts:
`<meta property="og:image" content="https://www.sistemalaser.com.br/assets/img/og-sistema-laser-2026.png">`
